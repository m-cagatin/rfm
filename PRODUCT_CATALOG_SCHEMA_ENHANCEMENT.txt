# Product Catalog Schema Enhancement Plan

## Overview

Fix and enhance the `catalog_clothing` table schema to properly support apparel products with colors, size-specific inventory, multiple images, and production details BEFORE implementing the ordering system.

## Current Schema Issues

### ❌ Problems Identified:

1. **No color support** - Each color is a separate product ("black t-shirt" vs "Plain White T-shirt")
2. **No size-specific inventory** - Can't track stock per size (10x Small, 5x Medium, 0x Large)
3. **Single image only** - Need front/back/detail views
4. **No material info** - Important for apparel (Cotton, Polyester, etc.)
5. **No production time** - Needed for job order estimates
6. **No customization flags** - Which products allow custom prints?
7. **No gender/fit type** - Men's, Women's, Unisex, fit styles

---

## ⚠️ POTENTIAL ISSUES & RISKS

### Critical Issues Identified:

#### 1. **Column Rename Breaking Change** ⚠️ HIGH RISK

**Problem:** Renaming `image_url` → `primary_image_url`

- **Backend code** uses `image_url` in 5+ places
- **Frontend code** uses `product.image_url` in templates
- **API routes** expect `image_url` parameter

**Impact:** BREAKS existing code immediately after migration!

**Solutions:**

- **Option A (Recommended):** Keep `image_url`, add NEW `images` JSON field
  ```sql
  -- Don't rename, just add new field
  ADD COLUMN images JSON DEFAULT NULL
  ```

- **Option B:** Rename but update ALL code references first
  - Update database.service.ts (5 occurrences)
  - Update catalog.routes.ts (3 occurrences)  
  - Update products.ts component
  - Update products.html template (4 occurrences)

**Recommendation:** Use Option A to avoid breaking changes.

---

#### 2. **MySQL ENUM Addition Limitation** ⚠️ MEDIUM RISK

**Problem:** Adding `gender ENUM('Men', 'Women', 'Unisex', 'Kids')`

- MySQL doesn't support `ADD COLUMN IF NOT EXISTS` with ENUM in all versions
- May fail on older MySQL versions

**Solution:**

```typescript
// Check if column exists first
const [columns] = await connection.execute(
  "SHOW COLUMNS FROM catalog_clothing LIKE 'gender'"
);
if (columns.length === 0) {
  await connection.execute(`
    ALTER TABLE catalog_clothing
    ADD COLUMN gender ENUM('Men', 'Women', 'Unisex', 'Kids') DEFAULT 'Unisex'
  `);
}
```

---

#### 3. **JSON Field Compatibility** ⚠️ MEDIUM RISK

**Problem:** Existing code sends `sizes` and `tags` as stringified JSON

- Current code: `sizes: JSON.stringify(sizes)`
- New fields (`colors`, `images`, etc.) will also need stringifying

**Solution:** Ensure consistency in handling:

```typescript
// In catalog.routes.ts
colors: colors ? JSON.stringify(colors) : null,
images: images ? JSON.stringify(images) : null,
stock_by_size_color: stock_by_size_color ? JSON.stringify(stock_by_size_color) : null
```

---

#### 4. **Stock Tracking Confusion** ⚠️ MEDIUM RISK

**Problem:** Two stock fields:

- `stock_quantity` (total)
- `stock_by_size_color` (per variant)

**Risk:** Data inconsistency - which is source of truth?

**Solution:** Make clear distinction:

- `stock_quantity` = Sum of all variants (calculated)
- `stock_by_size_color` = Actual inventory per SKU (source of truth)

**Add validation:**

```typescript
// Recalculate total stock from variants
const totalStock = Object.values(stock_by_size_color).reduce((sum, qty) => sum + qty, 0);
updateData.stock_quantity = totalStock;
```

---

#### 5. **Existing Product Migration Risk** ⚠️ HIGH RISK

**Problem:** 2 existing products will get default values

- "Plain White T-shirt" → colors: ["White"]
- "black t-shirt" → colors: ["Black"]
- But product names still say color!

**Solution:** Update product names too:

```typescript
// In migration script
if (product.product_name.toLowerCase().includes('white')) {
  await connection.execute(`
    UPDATE catalog_clothing
    SET product_name = REPLACE(product_name, 'White ', ''),
        colors = ?
    WHERE product_id = ?
  `, [JSON.stringify(['White']), product.product_id]);
}
```

- Users can't set colors, material, gender when creating products
- Will default to NULL or default values

**Solution:** Must update admin UI in same deployment:

- Add color picker/multi-select
- Add material text input
- Add gender dropdown

#### 7. **Foreign Key Constraints** ⚠️ LOW RISK

**Problem:** If `cart_items` or `order_items` tables exist (from customer ordering plan), they reference `product_id`

- Schema changes won't affect FK relationships
- But new fields won't be available in cart/orders yet

**Solution:** No immediate issue, but document that cart/order system needs updates later.

---

#### 8. **Cloudinary Integration** ⚠️ MEDIUM RISK

**Problem:** Multiple images means multiple uploads

- Current upload flow handles 1 image
- New flow needs to handle array of images

**Solution:** Update CloudinaryService:

```typescript
async uploadMultipleImages(files: File[]): Promise<string[]> {
  const uploads = files.map(file => this.uploadImage(file));
  const results = await Promise.all(uploads);
  return results.map(r => r.secure_url);
}
```

---

#### 9. **Database Size / Performance** ⚠️ LOW RISK

**Problem:** JSON fields with large data (images array, stock_by_size_color)

- May slow down queries if data is very large
- JSON parsing overhead

**Solution:**

- Monitor query performance
- Consider indexing if needed
- For now, acceptable risk (small catalog)

---

#### 10. **Backward Compatibility** ⚠️ HIGH RISK

**Problem:** Frontend expecting old schema while migration in progress

- If backend migrates but frontend not updated → errors
- Mobile apps or cached pages will break

**Solution:** Deploy in this order:

1. Run migration (add columns, keep `image_url`)
2. Update backend to handle BOTH old and new fields
3. Update frontend to use new fields
4. Later: deprecate old field names

---

## RECOMMENDED APPROACH: Keep `image_url`, Add New Fields

To avoid ALL breaking changes, let's use this SAFE migration:

```sql
ALTER TABLE catalog_clothing
  ADD COLUMN colors JSON DEFAULT NULL AFTER sizes,
  ADD COLUMN stock_by_size_color JSON DEFAULT NULL AFTER stock_quantity,
  ADD COLUMN images JSON DEFAULT NULL AFTER cloudinary_public_id,
  ADD COLUMN material VARCHAR(100) AFTER description,
  ADD COLUMN weight_grams INT AFTER material,
  ADD COLUMN gender ENUM('Men', 'Women', 'Unisex', 'Kids') DEFAULT 'Unisex' AFTER weight_grams,
  ADD COLUMN fit_type VARCHAR(50) AFTER gender,
  ADD COLUMN allows_customization BOOLEAN DEFAULT TRUE AFTER tags,
  ADD COLUMN customization_areas JSON DEFAULT NULL AFTER allows_customization,
  ADD COLUMN max_print_size VARCHAR(50) AFTER customization_areas,
  ADD COLUMN production_days INT DEFAULT 3 AFTER max_print_size;
```

**DON'T rename `image_url` to `primary_image_url`** - keep it as is!

- `image_url` = primary/main image (existing field, keep it!)
- `images` = array of additional images (new field)

---

## Implementation Order (SAFE APPROACH)

1. **Run migration** - Add new columns ONLY (don't rename anything)
2. **Update existing products** - Set default values for new fields
3. **Update backend** - Handle new fields (keep image_url working)
4. **Update routes** - Accept new fields in POST/PUT
5. **Update admin UI** - Add form fields for colors, material, etc.
6. **Test** - Verify old code still works + new features work
